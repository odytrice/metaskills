## Files and startup

Use `theme.css`, then `c4.css`. Load classic scripts with `defer`, in order:
`model.js`, `c4.js`, `c4-ui.js`. `document.js` is independent. No build, imports,
external JS libraries, network model requests, or server are required.

Register models in `window.PAPER_DOC_MODELS`. Each `<div data-c4="name">` mounts
that model. Optional `data-view` overrides the model's `initialView`. Multiple
explorers work independently. Keep a short textual architecture summary outside
the host so the document still communicates without JavaScript.

```html
<div data-c4="example" data-view="context">
  <p>The interactive model requires JavaScript. Read the summary below.</p>
</div>
```

`assets/template/model.js` is a complete fictional example. Copy and edit that
shape rather than inventing a schema. The sample's report service is not a fact
about the consuming project.

## Model schema

```js
window.PAPER_DOC_MODELS = {
  example: {
    name: 'Example service',
    description: 'Purpose of this model',
    status: 'Proposed',
    date: 'Use a real source date or revision',
    initialView: 'context',
    tags: { data: { label: 'Data', color: '#8a6200' } },
    elements: {
      user: { kind: 'person', name: 'User', desc: 'Submits a request.' },
      service: { kind: 'system', name: 'Example service', desc: 'Produces a result.' },
      api: { kind: 'app', parent: 'service', name: 'API', tech: 'HTTPS', desc: 'Handles requests.', tags: ['data'] },
      database: { kind: 'store', parent: 'service', name: 'Database', tech: 'PostgreSQL', desc: 'Persists results.' },
    },
    rels: [
      { from: 'user', to: 'api', label: 'Submits a request', tech: 'HTTPS / JSON' },
      { from: 'api', to: 'database', label: 'Stores results', tech: 'SQL / TLS' },
    ],
    views: {
      context: {
        level: 1, scope: 'service', title: 'System context', crumb: 'Context',
        layout: { user: [0, 100], service: [450, 100] },
        drill: { service: 'containers' },
      },
      containers: {
        level: 2, scope: 'service', title: 'Containers', crumb: 'Containers', parent: 'context',
        layout: { user: [-350, 100], api: [0, 100], database: [450, 100] },
      },
    },
    flows: [],
  },
};
```

Element IDs and view IDs use letters, digits, and underscores, starting with a
letter or underscore. IDs are stable references, not display names.

| Element field | Meaning |
|---|---|
| `kind` | `person`, `system`, `app`, `store`, or `component` |
| `parent` | Apps/stores belong to a system; components belong to one app/store |
| `name`, `desc` | Short name and concrete responsibility |
| `tech` | Technology or protocol, especially for C2/C3 |
| `external` | External software system, grey dashed outline |
| `supporting` | Hidden by default; toolbar can reveal it |
| `status` | Short badge such as `proposed` or `legacy` |
| `tags` | Array of tag names; ancestors inherit hidden descendant matches |
| `facts` | Array of verified factual statements for the inspector |
| `notes` | Object of prose; `why`, `tradeoff`, `improve` have accent styles |
| `files` | Array of source paths displayed as code, not automatic file links |

People and systems are top-level. Do not create fake containers to represent
classes or services that run in the same process. C4 level 4/code is not supported;
link to code instead. This is a small curated documentation viewer, not an editor
or an IcePanel-compatible model importer.

Relationships use `from`, `to`, `label`, optional `tech`, `async`, and `only` (an
array of view IDs). Use a directional verb phrase. Separate conceptually different
directions. `only` can provide an audience-specific context sentence without
repeating it in container views.

## Views and geometry

Each view needs `level` (1, 2, or 3), `scope`, `title`, and nonempty `layout`.
Optional: `ipTitle`, `crumb`, `parent`, `drill`, `labels: 'select'`,
`hideImplied`, `curves`, and `labelT`.

- `layout`: `{ elementId: [x, y, optionalSizeKey] }`. Coordinates are top-left.
- Native sizes: person 200x150, system 290x150, external 215x124,
  app/store 210x124, component 205x116, `sm` 178x92.
- Start around 400 to 450 horizontal and 300 to 350 vertical spacing. Leave
  space between a node and its labelled arrows. Keep names around 24 characters
  and descriptions to one or two short sentences; the inspector has full text.
- `scope`: system for C1/C2, app/store for C3. Child nodes get a dashed boundary.
- `drill`: `{ visibleElementId: 'childViewId' }`. `parent` defines breadcrumbs/up.
- `curves`: `{ 'source>target': 70 }` offsets the quadratic curve perpendicular
  to its midpoint. Negative values bend the other way.
- `labelT`: `{ 'source>target': .35 }` moves a label along its curve (0 to 1).
- `labels: 'select'` reduces noise in dense views. Selection or hover reveals
  labels, and the toolbar can show them all. This does not fix a bad layout.

The engine is manually laid out. It does not automatically route around nodes
or prevent crossings. Inspect every view after fonts load. Add curves or move
nodes if an edge, label, or boundary collides. Use several small views rather
than a single huge model. The full-surface SVG scales to fit; mobile users can
zoom and pan, but tiny diagrams still need a readable prose summary.

Connections between hidden descendants roll up to the nearest visible ancestor.
Dotted lines indicate a derived relationship; dashed lines indicate explicit
async relationships. The dotted roll-up notation takes precedence when both apply.
Relationships with the same visible endpoints are grouped; the first explicit
relationship (or first underlying one) supplies the headline label. Counts and
the inspector disclose the rest. This is a presentation simplification, not a
claim that all protocols/semantics are identical. Use carefully chosen explicit
context relationships or separate views when a grouped headline is misleading.

## Flows and filtering

```js
flows: [{
  id: 'submit', name: 'Submit a request', view: 'containers',
  steps: [
    { from: 'user', to: 'api', text: 'The user submits the request.' },
    { from: 'api', to: 'database', text: 'The API stores the result.' },
  ],
}]
```

`step.view` overrides `flow.view` to move between levels. Each endpoint must
have a visible ancestor in that view. Supporting endpoints are revealed for
the flow. Steps may show runtime direction not represented by a static edge;
the viewer draws a temporary path. Do not infer unsupported behavior from this.

Flows are manually started. Previous/next/dots are deterministic navigation;
optional Auto advances every 4.2 seconds. Reduced motion disables autoplay,
camera transitions, moving particles, and animated dashes. Tags highlight
elements without removing context. Starting a flow clears tag filtering;
navigating to another view stops the active flow.

## API and export

The auto-mounted instance is `host.c4Diagram`. For custom composition use
`PaperDocC4.mount(host, model, initialView)`, or the lower-level engine:

```js
const diagram = new C4Diagram(root, model, {
  onSelect(info) { /* info.e, info.rels, info.drill; null when cleared */ },
  onView(viewId, view) { /* update title and breadcrumbs */ },
  onStep(flow, index) { /* update narration */ },
});
await diagram.show('context');
```

Other methods: `drill(id)`, `up()`, `select(id)`, `clear()`, `fit(animate)`,
`zoomBy(factor)`, `setVocab('c4'|'icepanel')`, `setSupporting(boolean)`,
`setTag(tag|null)`, `setAllLabels(boolean)`, `startFlow(id)`, `step(index)`,
`stopFlow()`, `sentences()`, and `toDSL()`. Custom UI should serialize async
navigation like the bundled wiring does. `C4Diagram.validate(model)` checks
hierarchy, cycles, identifiers, references, layouts, and flow view coverage.

Export produces Structurizr DSL for hierarchy, relationships, static views,
and basic styles. It uses `autolayout lr`; it does not preserve manual positions,
runtime flows, inspector notes, view restrictions on relationships, or all tag
semantics. An export is a starting point for Structurizr, not round-trip storage.
Validate it with the target Structurizr version when downstream import is part
of the task. No external DSL parser is bundled or required to view the document.

## Verification

1. Open `index.html` via file URL. Check all local assets and browser errors.
2. Verify C1 title/scope/key and factual status. Inspect nodes and relationships.
3. Drill C1 to C2 to C3, use breadcrumbs and Up. Test Enter and Space on nodes.
4. Toggle labels, vocabulary, supporting systems, and each tag.
5. Pan, zoom, fit, and optionally enter/exit fullscreen.
6. Play a flow through a view change; verify previous/next/dots/stop. Check
   supporting endpoints and that changing views cancels playback.
7. Open DSL, copy or use the selection fallback, download, and close with Escape.
8. Test narrow width and reduced motion. Inspect hidden controls' focusability.
9. Check prose without JS and print mode. Printing includes the current graph
   view only; include static diagrams or prose if all views must be printable.
