The MetaSkills workflow, from raised issue to merged pull request

Four roles, thirteen skills.

Four agents carry every issue. A project manager defines it, an architect plans it, a developer builds it, and a separate architect reviews and merges it, while a QA agent files the bugs it finds back in as new issues. Each role works through a few narrow skills, hands off with evidence, and stops rather than guessing.

1The roles

Four agents do the work

Every step of the workflow is carried out by one of four agent roles, dispatched from your own session. Learn the roles first: the skills that follow are the playbooks they load, and the roles decide who may do what.

Plans and judges

architect

The judgment agent. In dev-cycle phase 1 it designs the How and claims the issue. In phase 3 a separate architect, with no context from the build, reviews the pull request and merges it.

Runs
issue-plan, code-review
Writes
The claim, the plan ledger, the review comment, and the squash merge. Locally, only .tmp-* staging files and the review worktree, both removed afterward.
Never
Writes production code, or reviews a change it implemented or substantially edited.
Returns
The ledger link, approach, task count, and blockers; or the review URL, assessment, and merge result.
Builds

developer

The implementation agent, dev-cycle phase 2. It turns the architect's plan ledger into one pull request, then fixes the reviewer's enumerated findings in at most two revision rounds.

Runs
issue-implement
Writes
A branch and commits in its own .worktrees/ checkout, the pull request, ledger check-offs, and the move to In review.
Never
Creates a plan ledger, claims an issue, or guesses. Ambiguity and design trade-offs go under the ledger's Blockers, and it stops.
Returns
The PR URL, changed paths, validation results, ledger state, and residual risks.
Defines and reports

project-manager

Owns the What. It files issues, refines them until they say what done means, and reports on the work. As a subagent it cannot hold a question gate, so it returns its questions for the caller to ask.

Runs
issue-raise, issue-refine, backlog-refine, weekly-review, project-status
Writes
New issues, and body, label, or status changes once approved. Locally, only Docs/ and .tmp-* bodies; its shell is read-only.
Never
Writes production code, or changes an issue body, labels, or board status without approval.
Returns
The issue URL, or a proposal with open questions; for reports, the file path.
Tests

quality-assurance

Tests a running app, staging by default, through Playwright MCP browser tools, and files only the bugs it can reproduce. burndown dispatches a fresh one to sweep a batch's merged work.

Runs
qa
Writes
One bug issue per root cause, filed through issue-raise. Edits and shell are unrestricted for testing.
Never
Drives the browser with scripts, npx playwright, or browser_run_code_unsafe; builds features; or captures secrets or personal data.
Returns
Workflows tested, issues filed, unfiled bugs with reasons, non-reproducible observations, and limits.
Not a role

You, the coordinator

The orchestrators dev-cycle and burndown are not agents. They run in your own session (burndown runs dev-cycle once per issue), dispatch each role with only the issue reference and the facts it needs, check what comes back, and dispatch the next. They never write code, post plans, move the board, or merge.

Without subagents, run each phase in a fresh session that loads only that phase's skill, and never review in the session that implemented. Two skills belong to no role: any session can run setup and paper-doc.

How each harness enforces the roles

Each role's instructions are identical in its Claude Code, opencode, and Codex definition, and lint checks that they match. The permission envelopes differ, because each harness expresses permissions its own way.

2The lifecycle

Five statuses, one owner per move

The board Status field is both the progress tracker and the lock. Each forward move belongs to one role, made through exactly one skill; the coordinator never moves it.

The What and the How

The issue body is the durable spec and never holds a design or a task list. The design lives in exactly one comment whose first line is <!-- plan-ledger -->. Only issue-plan creates it; everyone else edits it in place by its numeric REST id.

<!-- plan-ledger -->
## Plan
## Approach
## Touch Points
## Validation
## Risks
## Tasks
- [ ] Task: unit, code area, validation signal
## Sequence
## Blockers
_None._

Approach, Tasks, and Blockers are required. issue-implement starts only when Blockers reads _None._ and checks a task off only once it is implemented, validated, and in the branch.

The board moves in the figure are the only status writes in the whole workflow. dev-cycle, burndown, and backlog-refine dispatch the skills that make them, then verify the result.

Boardless projects

board: none is a declaration, not a default

A project that declares board: none in § Project Board skips every board read, claim, and move, and each skill reports that it did. Missing or incomplete board facts are different: they stop the skill, and are never reinterpreted as board: none.

Without a board, ownership still comes from the ledger and its tie-break, an existing ledger still needs an explicit resume, and the batch skills need an explicit list, label, or milestone because there is no Ready column to read.

3The skills

Thirteen skills in five groups

The skills are the roles' playbooks. Two define the work and three deliver it; three orchestrators sequence them for one issue or a batch; five more verify, report, or support.

Define the What

Say what done means

issue-raise files a classified, assigned issue at the board's new-issue status. issue-refine settles scope and acceptance criteria in the body, then moves it to Ready. Neither designs anything; design questions become constraints for the plan.

Deliver the How

Plan, build, review

issue-plan claims the issue and writes its plan ledger. issue-implement turns that ledger into one fully resolving PR. code-review, run by a different architect, reviews it and squash-merges when every criterion holds.

Orchestrate

Sequence, never do

dev-cycle runs the three delivery phases for one issue. burndown runs dev-cycle across dependency-ordered waves and closes with a QA sweep. backlog-refine fans issue-refine out across a backlog. None of them writes code, moves the board, or merges.

Verify and report

Feed findings back in

qa tests a running app through Playwright MCP and files each reproduced bug through issue-raise, so regressions re-enter the lifecycle at Backlog. weekly-review and project-status are read-only on GitHub and write only under Docs/status/.

Support

Outside the lifecycle

setup provisions local, Docker Compose, or CI environments from the documented commands. paper-doc writes portable HTML documents such as this one. Deployment is deliberately absent: it differs in every project, so it lives in the consuming repository.

Where the workflow stops on purpose

A required AGENTS.md section is missing
Any skill names the section and stops. Adding the section is the fix; the skill never infers it.
The issue is already claimed
issue-plan, dev-cycle, and burndown report claimed and leave it alone, even when the ledger looks abandoned. Only an explicit user resume continues it.
The plan needs a decision
issue-plan's approval gate triggers on materially different approaches with no clear winner, widened scope or a broken Notes constraint, a split, a data migration or backfill, a public contract change, a security or permission decision, or a What that is still ambiguous. It asks with a recommendation and stops before claiming.
Implementation hits a design question
issue-implement records it under Blockers and stops. dev-cycle may send the ledger back to the architect once, for a same-cycle repair; a second blocker ends the cycle.
Review cannot converge or merge
After two revision rounds, or as soon as the developer contests a finding, dev-cycle parks the PR with both positions. An unmet merge criterion short of Critical or High is reported and the PR stays open for the user.
The data is incomplete
A board read whose item count does not match totalCount, an issue URL with zero or several board matches, or a partial page set stops the operation. Samples are never reported as totals.
5One issue

dev-cycle, phase by phase

The coordinator writes no code, posts no plans, moves no status, and merges nothing. It dispatches each phase to a fresh context carrying only the issue reference and the facts that phase needs, then checks the result before the next dispatch.

PhaseRoleSkillSkipped whenReturns
1 · Planarchitectissue-planThe user explicitly asked to resume an already-planned issueLedger link, approach, task count, blockers or decisions
2 · Implementdeveloperissue-implementAn explicit resume finds an existing delivery PR, which goes straight to reviewPR URL, changed paths, ledger state, validation output, risks
3 · Reviewarchitect, distinct from phase 2code-reviewNeverAssessment, comment URL, merge or blocker, board transition, cleanup
4 · Revisedeveloper, then a fresh architectissue-implement, code-reviewThe review was cleanCommits, fixed and contested findings, validation output

What must hold before a merge

  • The assessment is Approve, with no Critical, High, or important pre-merge Medium finding.
  • Required checks pass on the reviewed head, and the PR is mergeable.
  • No validation result indicates production breakage.
  • Nobody asked for review only, and no auto-deploy needs manual timing.

The merge passes --match-head-commit with the reviewed SHA. If the head or base moved, the reviewer re-reviews a fresh pinned checkout instead of retrying with the new SHA.

Handoffs carry evidence, not context

Each dispatch prompt names the issue URL plus exactly what the next role needs: claim or resume evidence and the ledger's REST id for the developer, the PR number and round for the reviewer, the review comment URL and enumerated findings for a revision.

Without subagents, run one fresh session per phase, loading only that phase's skill. Never review in the session that implemented.

6Batches

Waves for delivery and grooming

burndown and backlog-refine both order their work into dependency waves. Neither restates or controls the skill it fans out to; each records results in the conversation and leaves state on the board.

burndown

Two bounds on concurrency

  • Scope, in precedence: an explicit issue list, a label query, a milestone, a board status the user names, else the Ready column.
  • Concurrency has exactly two bounds: dependency edges, and write-set overlap in files, migrations, contracts, routes, state models, or fixtures. Doubt serializes.
  • Decision points are recorded as needs-decision and asked together at the end of the wave; parked PRs block only their dependents.
  • Claimed elsewhere drops the issue and its dependents. Two or more in one wave stops the batch for a question.
  • The QA sweep is discovery, not a gate. Merged PRs are never reverted; confirmed bugs become new Backlog issues that reference the originating PR.

The coordinator's only GitHub writes are triage comments. Under GraphQL secondary rate limits it staggers board reads and prefers gh api graphql or REST verification over blocking the wave, then re-verifies unconfirmed moves once the limit resets.

backlog-refine

One gate, then waves

  • Nothing fans out before the gate, and no item is refined with an unanswered question or invented scope.
  • Only issue-refine edits a body, splits an issue, or moves it to Ready. backlog-refine writes nothing but .tmp-* bodies.
  • Each item is tracked as needs-answers, clarified, refined to Ready, skipped, or deferred, in the conversation.
  • Split parents are refined before their children, which land in later waves.
  • Obsolete or duplicate items are flagged for the user, never silently dropped.

Workers that cannot hold a question gate return their questions and the items already clear; the caller asks and re-dispatches with the answers.

7Ownership

How two agents avoid one issue

Claims are optimistic. The status is set first and re-read; then the plan ledger's numeric REST comment id settles any tie that the status could not.

Reading the board

Before any status edit, read the board's totalCount, fetch exactly that many items, and require the counts to match. Match the issue by its canonical URL, never its number. Zero matches asks; several matches stop as ambiguous.

Resume and repair

A ledger is never silently resumed, however stale it looks. The one coordinator exception is a same-cycle blocked-plan repair: dev-cycle passes the ledger's REST id, its ownership evidence, and the blockers, and the architect edits that ledger under the same approval gate.

Residual raceBoard moves and ledger edits are not atomic. Re-reading and the tie-break narrow the race without closing it, so ambiguous ownership stops rather than overwrites. Two burndowns on one scope degrade to skipped issues, not duplicate PRs.
